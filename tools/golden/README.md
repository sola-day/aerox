# tools/golden — golden corpus generators

Everything under `test/golden/` is listed in `test/golden/MANIFEST.json` with its
provenance (VERIFICATION.md §2.2). Two kinds of files live there:

- **Copied** (`kind: "copied"`): vendored verbatim from a pinned commit of the upstream
  reading-room checkouts (`../bsky/atproto`, `../bsky/indigo`, `../bsky/did-method-plc`)
  by `tools/golden/vendor.py`. Re-run `python3 tools/golden/vendor.py` to refresh them
  and their manifest entries.
- **Generated** (`kind: "generated"`): produced by running upstream library code inside
  a pinned container, so results do not depend on a developer's toolchain.

## DAG-CBOR and CID vectors (`test/golden/dagcbor/`, `test/golden/cid/`)

Generated by `tools/golden/ts/` against `@ipld/dag-cbor` and `multiformats` (exact
versions pinned in `package.json` / `package-lock.json`). Regenerate with:

```sh
tools/golden/ts/run.sh
```

which runs `npm ci && node gen-dagcbor.mjs && node gen-cid.mjs` in
`node:24-alpine (pinned by digest in run.sh)` with the repo root mounted at `/work`. If that tag cannot be
pulled, pick another image with `GOLDEN_NODE_IMAGE=node:24-alpine tools/golden/ts/run.sh`
and record the image (and its digest) in the manifest entries.

- `dagcbor/<name>.json` — input value in atproto JSON form (`{"$link": …}` for CIDs,
  `{"$bytes": …}` for bytes, base64 without padding)
- `dagcbor/<name>.cbor` — the exact `@ipld/dag-cbor` encoding
- `dagcbor/<name>.cid` — CIDv1 dag-cbor/sha256, base32 string, no trailing newline
- `cid/vectors.json` — block bytes, codec, CID string, CID binary, and the tag-42
  encoding of `{"x": <cid>}` (which must carry the `0x00` multibase-identity prefix)

The test values themselves are in `tools/golden/ts/values.mjs`. Never edit a golden by
hand: change the generator (or follow an upstream change), re-run it, and update the
manifest hashes (`vendor.py` refreshes the sha256 of `generated` entries too).
